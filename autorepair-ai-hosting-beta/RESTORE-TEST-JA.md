# 0.14.2 — 復元テストの自動化

## できること

既存の「サイト全体」保存ポイントを、新しい隔離コンテナーのファイル領域とMySQLへ復元して確認します。本番のファイルやDBには復元しません。管理画面の保存ポイントごとに、次の状態を表示します。

- 保存成功／復元テスト未実行
- 保存成功／復元テスト実行中（強制終了時は未完了）
- 復元テスト合格（隔離環境）
- 保存成功／復元テスト不合格
- 保存成功／テスト環境未準備
- 保存成功／テスト記録を確認できません（記録の改変・保存元の変化等）

合格には、ファイル照合・全対象テーブルの件数と内容の照合・トップページHTTP 200とHTML・WordPress起動を示す実行ごとの応答ヘッダー・一時環境の削除がすべて必要です。結果は保存元manifestのハッシュに結び付け、HMACで署名します。前回合格した保存でも再検証を始めると実行中へ変わり、その回が失敗すれば不合格になります。最新の結果を保持する方式です。

## 初回だけ必要な準備

この機能にはLinux上のローカルDocker Engine、Python 3.11以上、WP-CLI、PHPのproc_openが必要です。Dockerを操作できる権限はサーバーへの強い権限なので、WebサーバーのPHPユーザーへ付与せず、サーバー管理用のCLIアカウントから実行してください。共有レンタルサーバーでは利用できない場合があります。別ホストへの遠隔実行・Docker Desktop・本番と異なるDB形式は本試作の対象外です。

最低でもDB用1GiBとPHP用512MiBに加え、OS・元のWordPress・コピー展開用の余裕が必要です。DB一時領域は4GiB、PHP一時領域は128MiBに制限しています。大きなDBや大量の行は制限に達してテスト不合格になる場合があります。大規模性能は実証していません。

1. 0.14.2をインストールし、0.13.0と同じ公開領域外の保管先を設定します。
2. 「バックアップ・復元 → 復元コマンドを保管場所へ配置」を押します。旧版で配置済みでも、今回もう一度押してください。
3. 保管先に配置された `restore-test` ディレクトリで、サーバー管理用CLIから次を実行します。

```bash
docker pull mysql:8.4
docker build -t aaihb-restore-test:0.14.2 /実際の保管先/restore-test
```

初回のイメージ取得・作成にはインターネット接続が必要です。検証実行中はイメージを自動ダウンロードしません。必要なイメージがなければ「テスト環境未準備」にします。

## 保存済みバックアップを検証する

WordPressのディレクトリで、実際の保管先と保存IDに置き換えて実行します。保存ポイントを読む検証なので、本番の書き込み停止は不要です。

```bash
wp --skip-plugins --skip-themes --require=/実際の保管先/vault-command.php aaihb-vault verify 保存ID
```

実行後、「バックアップ・復元」を再表示すると判定を確認できます。本番への復元コマンド `restore` とは別の `verify` です。

## 保存直後に自動で検証する

既存のバックアップ操作に `--verify` を付けます。バックアップ自体は従来どおり、Web・ジョブ等の書き込みを停止した状態で実行してください。

```bash
wp --skip-plugins --skip-themes --require=/実際の保管先/vault-command.php aaihb-vault backup --ack-quiesced --verify
```

保存 → 隔離環境作成 → ファイル展開 → DBインポート → DB照合 → ページ確認 → 後片付け → 結果記録まで自動で進みます。検証に失敗しても成功済みの元バックアップは消しません。定期バックアップのスケジューラーは今回の追加範囲には含みません。

## 隔離する方法と、合格の範囲

MySQLとPHPの両コンテナーをDockerの `--network none` で起動し、TCPによる外部接続・公開ポートを持たせません。両者のDB通信には専用のUnixソケット用一時ボリュームを使います。Dockerソケット、本番ディレクトリ、バックアップ保管先はコンテナーへマウントしません。一時コピーだけを渡します。

元のwp-config.phpは実行せず、複製用のDB接続設定・URLへ置き換えます。cron・自動更新・メール送信を止め、MUプラグインと `db.php`、`object-cache.php`、`advanced-cache.php`、`sunrise.php` は複製環境で無効化します。通常の有効プラグイン・テーマは複製DBの設定に従って読み込みます。

したがって「合格」は、この変更を加えた隔離環境での復元・DB内容・トップページの基本応答についての結果です。完全に同じ本番構成での復元、ブラウザー上の画像・CSSの見た目、フォーム、注文、会員ログイン、メール、外部決済、MUプラグイン、キャッシュ基盤の動作までは保証しません。外部サービスが必須のサイトは本機能では合格しない場合があります。

## 失敗時の見方

| 確認段階 | 確認すること |
|---|---|
| preflight / テスト環境未準備 | Dockerが起動しているか、CLI権限、2つのイメージがあるか |
| files | バックアップの破損、展開容量、ファイル数・サイズ |
| isolation | Dockerのボリューム・コンテナーを作成できるか |
| database_start | MySQLを起動できるメモリー・一時容量があるか |
| database | インポートできるスキーマ・文字コード・データか、復元内容が一致するか |
| homepage | テーマや通常プラグインが隔離環境で起動するか、外部接続必須ではないか |
| cleanup | 一時コンテナー・ソケットボリューム・一時コピーを削除できたか |
| runner | Python、proc_open、実行ツールの配置・結果形式を確認 |

SQL、ページ本文、認証情報を結果画面へ出しません。バックアップと複製には顧客データや設定値が含まれるため、サーバー管理者だけがアクセスできる環境で使用してください。

通常終了・検知できた失敗時は、この実行で作ったコンテナー・ボリューム・一時コピーを削除します。強制終了やDocker停止では残る場合があります。保存ポイント内の `restore-test.json` の `resources` がその実行の識別子です。同じ識別子に `-php`、`-db`、`-socket` を付けたリソースだけを確認し、管理者が後片付けしてください。無関係なDockerリソースの一括削除は行いません。

## 今回の検証状況

開発環境にDocker Engineがないため、実Docker・実MySQL・実WordPressを一体で起動した復元テストは未実行です。Pythonの実行制御・異常判定のテストと、WordPress Playground上での判定記録・改変拒否・画面表示を検証しています。実環境で「合格」が出たことを意味するサンプル実績は付けていません。初回は、サーバー管理者が管理できる複製用途の環境で動作確認してください。
