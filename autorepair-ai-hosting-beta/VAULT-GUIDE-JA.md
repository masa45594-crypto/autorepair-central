# AutoRepair AI Hosting Beta 0.13.0 — バックアップ・復元の使い方

この版は試作です。AutoRepair AI本体を必要とせず動きます。プラグインファイルの退避・復元と、同一サイトのファイル＋DBの保管・復元を追加しました。

## 最初に知っておくこと

- プラグインの保存・復元は管理画面「バックアップ・復元」で操作します。
- サイト全体の保存・復元はサーバーのWP-CLIで操作します。画面のワンクリック全体復元はありません。
- 実MySQLを使った通し復元・停電時の復旧・本番負荷は未検証です。複製環境での復元試験が必要です。
- このプラグインを入れたサイトだけが修復対象です。Hubから別サイトを一括復元する機能ではありません。
- 全体復元をすると、保存後の投稿・注文・会員情報等も保存時点へ戻ります。復元直前の全体バックアップと退避ファイル・退避テーブルを残します。

## 1. 保管先を設定する

公開ディレクトリの外に、PHPの実行ユーザーが読み書きできる専用フォルダーを作り、権限を0700にします。公開ルートとはWordPressフォルダーだけでなく、そのサーバーでWeb公開される範囲全体です。別のWebサイトやエイリアスでも公開しないでください。

wp-config.phpの「編集を終了」の行より前に、実際のパスを指定します。以下のパスは例で、そのまま使えるとは限りません。

```php
define('AAIHB_VAULT_DIR', '/srv/private/autorepair-vault');
define('AAIHB_PUBLIC_ROOT', '/srv/www');
```

保管先とサイトは同じファイルシステム上に配置します。ZipArchive、十分な空き容量、親ディレクトリへの書き込み権限が必要です。SSH/WP-CLIを使えないサーバーでは全体復元は使えません。

保管データにはDB、認証情報を含むwp-config.php、投稿、顧客データが含まれます。ZIPは暗号化していません。公開しないでください。manifestのHMACと各ファイルのSHA-256で破損・改変を検出します。vault.keyが失われると保存ポイントを認証できません。サーバー全体の故障に備える別サーバーへのコピーは本版に含まれません。

## 2. プラグイン更新前の保護

1. 「バックアップ・復元」を開く。
2. 「このプラグインを保存」で、複製環境にある対象を保存する。
3. 保存IDを確認する。
4. 「更新前保護を有効にする」を押す。
5. WordPressの通常の更新操作を行う。

保護が有効なとき、更新前の保存に失敗すると更新を停止します。単一ファイル形式のプラグインとHosting Beta自身は対象外で、その更新も停止します。必要なら保護を停止したうえで、サーバーのバックアップを用意して通常更新してください。

自動復元の条件は、対象1個だけの更新・1時間以内・更新前HTTP 2xx・更新直後に連続2回HTTP 5xxです。タイムアウト、403、リダイレクト、内容の崩れ、後日発生したエラーは自動復元対象になりません。一括更新は更新前保存のみです。更新後にファイルが変わっていれば自動復元を止めます。

5xxの原因がそのプラグインであると断定する仕組みではありません。差し戻した後、公開画面・管理画面を確認してください。CDNキャッシュ、複数サーバー、外部ストレージがある環境は別途検証が必要です。バックアップは更新を行うプロセス内で実行するため、大きなプラグインではPHPの実行時間・メモリー上限に達する場合があります。

## 3. プラグインを手動で戻す

保存済みポイントで対象名とIDを確認し、確認欄をチェックして「この時点のファイルに戻す」を押します。対象プラグインのディレクトリ全体を戻します。DBスキーマや設定・投稿は戻りません。更新がDB移行を伴う製品では、ファイルだけの差し戻しが適切か事前確認してください。

元のファイルは保管領域の操作ID/previousに残ります。更新版に戻したい場合は、この退避フォルダーをサーバー側で確認してください。退避履歴の自動削除や、画面からの再差し戻しは未実装です。

## 4. サイト全体を保存する

本機能のDBはMySQL 8.xまたはMariaDB 10.5以上のInnoDBテーブルに対応します。MyISAM・外部テーブルスペース等は対象外です。DBユーザーにSELECT、SHOW VIEW相当の構成確認、TRIGGERの確認、LOCK TABLES、CREATE、INSERT、ALTER、DROP等の権限が必要です。

単一サイト、WordPress直下のwp-config.php、サイト内のwp-contentが対象です。シンボリックリンク・特殊ファイル・外部ディレクトリ・マルチサイト・DBビュー・トリガー・外部キーは対象外です。サイト外のメール、DNS、Webサーバー設定、外部ストレージ、別接頭辞のテーブルは含みません。ファイル5万項目・合計2GiB、DB合計2GiB・JSONL1行16MiBの上限があります。

1. サーバー側でWebからの書き込みを止め、外部cron・ワーカーを停止し、実行中処理が終わるのを待ちます。WordPressの.maintenanceだけではすべての書き込みを止められません。
2. 管理画面で「復元コマンドを保管場所へ配置」を押します。プラグインを更新したら配置し直します。
3. サイトのディレクトリで、以下のパスを実環境に置き換えて実行します。

```bash
wp --skip-plugins --skip-themes --require=/srv/private/autorepair-vault/vault-command.php aaihb-vault backup --ack-quiesced
```

DBテーブルをREADロックしている間にDBとファイルを保存し、ファイル一覧・サイズ・ハッシュが変化していないことを確認します。成功すると保存IDを表示します。停止を解除する前に成功を確認してください。

## 5. サイト全体を戻す

同じパス、同じDB名、同じ接頭辞への復元専用です。移行ツールではありません。保存したwp-config.phpのDB接続情報が今も有効であることを確認してください。

1. 全書き込みを停止します（上記と同じ）。
2. 現在のファイル＋DBをもう1組保存するための空き容量を確保します。旧・新データと展開領域が同時に残ります。
3. 保存IDとサイトの絶対パスを指定します。

```bash
wp --skip-plugins --skip-themes --require=/srv/private/autorepair-vault/vault-command.php aaihb-vault restore 保存ID --ack-quiesced --confirm-site=/srv/www/wordpress
```

先に現状の全体バックアップを作り、保存したファイルとDBを別領域で準備してから切り替えます。DBの切り替えが例外を返した場合は、ファイルを直前状態へ差し戻します。成功時は復元ID・直前バックアップID・処理記録IDが表示されます。

4. PHP OPcache・ページキャッシュ・CDNキャッシュをサーバー側で更新し、公開画面、管理画面、投稿、フォーム、注文機能を確認します。
5. 確認後にWebアクセスとジョブを再開します。

WP-CLIが起動できるWordPress本体とDB接続が必要です。MUプラグイン・drop-inは--skip-pluginsでも読まれる場合があります。本体やDB接続自体が壊れてWP-CLIが起動できなければ、サーバー側の外部バックアップから復旧してください。

## 中断・失敗した場合

処理が強制終了するとファイルとDBの一方だけが切り替わっている可能性があります。自動で再実行せず、書き込み停止を維持して、保管領域のrestore-journal.jsonを確認します。

- prepared：準備中、またはファイル切り替え直後の記録前に中断した可能性。
- files_published：ファイル切り替え済み。DB切り替えの完了記録前に中断した可能性もあります。
- complete：切り替え完了を記録。

ファイルはprevious-site、以前のDBテーブルはahb_hold_で始まる名前に退避します。ahb_stage_は準備用テーブルです。記録のmapping、db_token、previous_tablesと実際のDBテーブルを照合して状態を判断します。これらの退避物を確認せず削除しないでください。中断からの自動復旧は未実装です。

## AutoRepair AIから引き継いだ機能

| 機能 | Hosting Betaの対応 |
|---|---|
| 診断 | 内蔵10項目。AutoRepair AI本体不要 |
| 修復 | リライトルール再生成、古い標準メンテナンスファイルの解除 |
| 変更前の復元点 | リライトルール・メンテナンスファイルを既存0.12方式で記録 |
| 自動修復 | 明示的に有効化した場合の空リライトルール再生成。無制限なコード修正は行わない |
| キャッシュ削除 | オブジェクトキャッシュのみ。外部CDN等は対象外 |
| 更新情報の再取得 | 更新情報キャッシュ削除 |
| 定期診断の予約 | このサイトの毎日診断を有効化・再予約・停止 |
| 更新前保存・ロールバック | 本版で追加。対象・条件は上記 |
| 全体バックアップ・復元 | 本版で追加したWP-CLI試作。実DBでの復元検証は残る |

本体の全機能・全環境互換を証明した版ではありません。既存の接続台帳、案件、価値記録、中央利用数管理は継続します。決済を本番稼働させる変更は含みません。
